| CART-001 | 2026-09-29 | Serialize client cart mutations until the backend returns its authoritative cart result | Overlapping quantity/clear actions can race on a weak connection and make a stale client response visible | Cart state remains backend-authoritative and conflicting controls wait for the in-flight result | Yes; revisit with a deliberate queued or optimistic cart architecture |
| ADDRESS-001 | 2026-09-29 | Serialize one web address-save submission through serviceability, create, and reload | A weak connection can leave the Add-address form live while the first create request is pending, allowing duplicate concurrent addresses; a refresh failure after a confirmed create can hide the returned address | A second submit cannot start another serviceability or create request, and the confirmed response updates the visible address state before reload; backend serviceability and ownership remain authoritative | Yes; add a durable address retry/idempotency contract only with an explicit backend design |
| SUPPORT-001 | 2026-09-29 | Support-ticket creation accepts an optional client key and enforces uniqueness by `(user_id, idempotency_key)` | A forced duplicate submit or an uncertain response can otherwise create duplicate support cases; requiring the new field immediately would break existing clients | An identical request safely replays one ownership-checked ticket, a changed payload receives `409`, and the web client retains the key across an in-page retry while serializing ticket/reply submits | Yes; consider durable cross-restart retry only with an explicit client persistence design |
| PAYMENT-001 | 2026-09-30 | Serialize payment-intent creation by locking the authenticated commercial order; make verification and webhook take the same Order→PaymentAttempt lock order; serialize the web Pay-now action | A concurrent intent retry can otherwise create separate provider orders before either request records its attempt, and reverse attempt/order locks can deadlock a retry with a provider result; a forced client event can initiate a duplicate request before React disables the button | One request owns the order lock and reuses the resulting attempt for later callers; all payment mutation paths share a lock order; client control state is a convenience while the backend owns payment, order, and provider authority | Yes; revisit a durable provider-create recovery protocol only with an explicit provider-idempotency design |
| PAYMENT-002 | 2026-09-30 | Render a payment-intent `503` for an existing pending UPI order as neutral recoverable availability, not provider configuration detail | Provider configuration is an operational detail, and an unavailable intent does not change the server-authoritative order or payment state | The customer sees that the order remains saved and payment pending, raw detail is suppressed, and Pay now is restored for a later server-mediated retry; the backend remains authoritative for eligibility, status, and configuration | Yes; revisit only with an explicit payment-recovery design |
| PAYMENT-003 | 2026-09-30 | After a successful new UPI checkout, map only its initial payment-intent `503` to the existing neutral pending-order recovery path | Checkout has already created the authoritative order when an unavailable provider/configuration can return raw operational detail; mapping checkout failures, non-`503` errors, or verification outcomes would hide distinct states | The visible order remains server-authoritative and payment pending, raw provider detail is suppressed, and a later Pay now request returns through the existing server intent boundary; roles, ownership, provider configuration, and all other errors remain unchanged | Yes; revisit only with an explicit payment-recovery design |
